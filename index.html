1. Start here: backend drives the UI

Default to the backend as source of truth. A click fires @get/@post, the backend returns SSE that patches elements. No frontend state needed. data-indicator gives you loading for free.

Try it

⏳ loading…
…
slow result lands here

Code

<button data-on:click="@get('/api/slow')"
  data-indicator:s1_loading>Slow fetch</button> $s1_loading=
<span data-show="$s1_loading">⏳ loading…</span>
<div id="s5_counter">…</div>

# backend returns SSE:
event: datastar-patch-elements
data: elements <div id="s5_counter">42</div>
Pattern: one request → 0..n SSE events. Patch HTML with morphing (send fat HTML, only diffs apply). Use data-indicator:name on the same element that fires the action — Datastar sets $name=true while that element's request is in flight (it matches fetch events by element identity, so a wrapper div won't catch child buttons). Read it anywhere with data-show="$name". Reach for signals only when you need client reactivity (next).

2. Reach for signals: reactivity & forms

When the UI must react without a round-trip — typing, toggles, conditional buttons — add signals ($name). They stay on the client until you send them.

Try it

Hello, !

qty is 0 — button hides via data-show.

✅ Order placed: item(s) for .

Code

<button
  data-show="$s2_qty > 0" $s2_qty=
  data-attr:disabled="!$s2_agree" $s2_agree=
  data-on:click="$s2_placed = true" $s2_placed=
>Checkout × <span data-text="$s2_qty"></span>
</button>
<p data-show="$s2_placed">
  ✅ Order placed: <strong data-text="$s2_qty"></strong>
</p>
<p>Hello, <strong data-text="$s1_name"></strong></p> $s1_name=
When signals: data-bind (two-way input) → data-text / data-show / data-class / data-attr (display). Signals are global; $_local prefix keeps them client-only (never sent). Tip: pair data-show with style="display:none" to avoid flash.

3. Combine: signals sent to backend

All non-_ signals ship with every @get/@post (query ?datastar={…} or JSON body). Classic example: debounced active search.

4. When expressions get big → plain JS

Datastar expressions are JS-like, but for reuse/tests/multi-line logic extract to window.App. Pass signals as arguments, use the return value.

Try it

slug:

words: · shouty:

Code

// plain JS — testable, reusable
window.App.slugify = (s) => s.toLowerCase()
  .trim().replace(/[^a-z0-9]+/g,'-').replace(/^-|-$/g,'');

<input data-bind:s3_title $s3_title=
  data-on:input="$s3_slug = App.slugify($s3_title)" /> $s3_slug=
<span data-text="App.wordCount($s3_title)"></span>
Rule: sync helpers → return a value. Async → can't be awaited, so dispatch a CustomEvent (next step).

5. Async JS: events up

Datastar won't await async code. Helper takes (el, data), works, then el.dispatchEvent(new CustomEvent(...)). Datastar listens with data-on:myevent.

Try it

result:

Code

<input data-bind:s4_q $s4_q=
  data-on:input="App.fakeLookup(el, $s4_q)" />
<div data-on:fakelookup__window="$s4_result = evt.detail.label"></div> $s4_result=

async function fakeLookup(el, q) {
  await sleep(400);
  el.dispatchEvent(new CustomEvent('fakelookup',
    {bubbles:true, detail:{label: `Found: ${q}`}}));
}
Pattern: props down (args) → event up (detail). Same shape as web components.

6. Encapsulate complexity: web components

Stateful/complex UI (pickers, editors, charts) → native web component. Datastar coordinates via signals as props down (data-attr:) and events up (data-on:). Component knows nothing about Datastar.

Try it — <color-picker>

signal:

Code

<color-picker
  data-attr:value="$s7_color" $s7_color=
  data-on:color-input="$s7_color = evt.detail.value"
></color-picker>

class ColorPicker extends HTMLElement {
  static observedAttributes = ['value'];
  attributeChangedCallback(n,o,v){ /* render */ }
  #emit(v){ this.dispatchEvent(new CustomEvent('color-input',
    {bubbles:true, composed:true, detail:{value:v}})); }
}
Contract: plain attributes in, CustomEvent(bubbles, composed) with detail out → mapped to a signal. Also works with data-bind if the component exposes value + fires change.
